## Findings

### SEC-13 — Бэкап, на который ссылается предупреждение о пропавших чужих записях, содержит ту версию прежнего файла, по которой эти записи посчитаны, и не затирается другим бэкапом той же пересборки

**Суть.** В раунде 2 пересборка стала циклом до трёх попыток, а бэкапы остались «не больше одного раза за пересборку» (флаги `lostSaved` и `unreadableSaved`). Список пропавших записей (`lost`) и предупреждение берутся из последней попытки, а бэкап — из первой попытки, где `lost` оказался непустым. Если между попытками файл изменился (ровно этот случай и запускает повтор), бэкап и предупреждение описывают разные версии файла. Второе: `backupFile` называет файл с точностью до секунды и перезаписывает существующий (`os.WriteFile`), а попытки идут в пределах миллисекунд. Поэтому бэкап нечитаемого файла из попытки 2 затирает бэкап с чужими записями из попытки 1. В `resolution.md` раунда 2 совпадение имён бэкапов названо недостижимым («в одной пересборке оба случиться не могут») — в одной попытке это так, а между попытками достижимо.

**Места:**
- `pkg/initstate/run.go:291-294` — `if len(lost) > 0 && !lostSaved` защёлкивает бэкап на первой попытке; на следующих `lost` пересчитывается, бэкап — нет.
- `pkg/initstate/run.go:267-275` — бэкап нечитаемого файла в более поздней попытке пишет в то же имя.
- `pkg/initstate/run.go:305-311` — предупреждение по `lost` последней попытки с путём бэкапа из более ранней.
- `pkg/initstate/run.go:350-351` — имя бэкапа с точностью до секунды, существующий файл перезаписывается.
- Спека, шаг 8: «Бэкапы шагов 4 и 8 делаются не больше одного раза за пересборку» — правило записано намеренно, но последствия для повторов в нём не учтены.

**Сценарии (оба воспроизведены harness'ом).**
1. *Устаревший бэкап.* В `kc.yaml` есть чужая запись `f1`. Попытка 1 находит `f1` пропавшей и делает бэкап. Неатомарный писатель без lock (например, `aws eks update-kubeconfig` с `KUBECONFIG=kc.yaml`) дописывает `f2`, перепроверка это видит, попытка 2 находит `[f1 f2]`. Итог: stderr «нет записей …: [f1 f2]; прежний файл сохранён: …backup.20261016-131918», в бэкапе `f1=true f2=false`, в `kc.yaml` нет обеих. `f2` потеряна, хотя запись замечена до последнего `stat`, — это вне остатка, который описан в решении по SEC-12.
2. *Затёртый бэкап.* В `kc.yaml` есть `f1`. Попытка 1: `lost=[f1]`, бэкап B. Пока идёт попытка, файл переписывают неатомарно (truncate + write) — попытка 2 читает его недописанным, YAML не разбирается, «прежний файл сохранён: B» — тот же путь, теперь в B недописанный файл. Запись заканчивается, попытка 3 снова находит `lost=[f1]`, но `lostSaved` уже стоит. Итог: два предупреждения со ссылкой на один и тот же B; в B невалидный YAML без `f1` (`loadErr=yaml: line 20: did not find expected node content`), в `kc.yaml` `f1` нет. Креды `f1` не сохранились нигде.

**Почему minor.** Нужны сразу три условия: в `kc.yaml` есть чужие записи, которые пропадают (сценарий SEC-02), и неатомарная чужая запись в окне в несколько миллисекунд под lock client-go, а для сценария 2 — ещё и чтение файла посреди этой записи. На практике это почти невероятно. Но если это всё-таки случится, данные теряются безвозвратно, а stderr уверяет, что копия есть, — поэтому это не «шум», а дефект с адресом.

**Как чинить.** Делать бэкап для `lost` по той версии файла, по которой посчитан `lost` последней попытки: например, бэкап, если `lost` непуст и `before` отличается от stamp файла на момент предыдущего бэкапа (или просто на каждой попытке с непустым `lost`, но без затирания). `backupFile` не должен перезаписывать существующий файл: добавить к имени суффикс (`-2`, наносекунды) или открывать с `O_EXCL` и повторять с другим именем — `revert` по префиксу имени их всё равно найдёт. Тесты: через `beforeWriteHook` дописать чужую запись в попытке 1 — бэкап содержит её; в попытке 1 сделать файл нечитаемым после бэкапа `lost` — в `backups/` остаётся копия с чужой записью.
